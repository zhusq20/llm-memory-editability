# 用户指定GPU7的调度修订

用户在原六臂仍全部等待、尚无任何GPU阶段时明确要求：“直接用7号卡先跑起来，其余任务等有空闲GPU再自动并行启动。”本修订只调整资源准入与等待控制器，不修改原冻结配置、输入、训练/评分源码或科学矩阵，不重复任何已完成阶段。

最初GPU7显存/利用率均0、无CUDA进程，但default daemon中两个旧评测容器仍保留GPU7设备记录，导致原严格预留判断拒绝它。接管期间另一批CE检查及旧评测恢复实际运行；用户指定的第一臂`loop-lr2e-4`因此按共卡调度，保留所有现有容器和CUDA PID。其余五臂继续等实际空闲卡，并在其它卡释放后自动并行。

GPU7第一臂使用本批独立共卡锁，不删除、不改写另一批持有的`/tmp/lm-memory-gpu-locks-1015/gpu-7.lock`。其余本批任务必须同时尊重本批GPU7锁和原全局锁。仅第一臂允许GPU7已有进程/预留，并要求至少24GiB实际空闲、原CPU/主存检查及完整CUDA preflight、32步原尺寸短训与独立重载通过后才正式训练。其余五臂保留原80,000MiB空闲、无CUDA PID/低显存利用等准入；只忽略已记录的两个default旧容器在GPU7上的设备预留，真实占用仍阻止准入。

24GiB是本次指定共卡的工程准入，不是已建立的显存需求测量；全尺寸验证若OOM或数值失败，保留失败、不自动修改科学配方重试。每阶段保存真实显存、利用率与已有GPU PID，`exclusive_idle_gpu=false`，共卡耗时不当作独占GPU效率基准。保持原学习率、匹配衰减、样本流、初始化、裁剪、300k步数和审计要求。

六项针对性调度测试、Ruff检查/格式检查通过，包含锁保留、指定臂共卡、真实占用记录、24GiB下限、CPU碰撞拒绝及非7号卡规则不变。原source-manifest保持`d057cc10f615ea8c87978d58bb56f610aae6127b94336411d073083365e28ba3`，原配置保持`5d71382bf5b2b678e72dcf9706b93ce4f6fde0aebc2d80ed319736d16d3399f8`。
